# 决策记录 0004：每人一个 MVP，怎么选基线

> 状态：提议，待组会。整理：ClawsGO Science Agent，2026-11-24。

## 背景

组长 2026-11-23 的安排：现在每个人出一个 MVP，然后商量定基线。`people/` 下已有几个 MVP 或原型，技术栈各不相同。没有统一的尺子，讨论容易变成比谁的页面好看，或者谁的声音大。

## 提议：同一把尺子，不比谁写得多

1. 每个 MVP 的作者按同一份脚本演示，不超过 5 分钟：首页，听一段声，留一段声，看社区那一层，换成手机宽度再走一遍。
2. 现场按 `docs/design/评分口径与MVP验收.md` §6 的 A1 到 A10 逐项记：通过、未通过、未验证。每项写证据（命令输出、截图或文件路径）。
3. 另加三个问题，因为它们决定基线能不能接着做：
   - 数据读写是不是集中在一处？接后端时要改几个文件？
   - 模块边界是不是清楚？能不能按模块分给六个人，各改各的目录？
   - 手机 375px 宽度下，能不能从首页走到"听"和"留"？
4. 现在还没有线上地址，也没有后端，所以 A1 用本地预览代替（构建后打开，任一子页面按 F5 不白屏），A4 不参与比较。
5. 否决项：A3（无死按钮、控制台 0 报错）和本地版 A1 不过的，不能当基线，要先补到过。
6. 其余按通过的项数比较。接近的时候，倾向数据读写集中、模块边界清楚的那一个，因为接下来的时间主要花在后端和分工上。

## 落选的 MVP 怎么办

不浪费。每个 MVP 里被组会认可的亮点，列成"并入清单"：并入基线的哪个模块，谁来并。作者署名和 PR 记录保留，这同时是分工的证据（评分表「分工」10 分）。
