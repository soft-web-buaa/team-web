# 《走进软件》六人团队 · Web 选题推荐（整理与详解）

> **来源**：`web-ideas-book/《走进软件》6人团队-Web选题推荐.pdf`（v2.0，共 5 页）
> **整理**：Confused-Tree（CdT）
> **阅读约定**：标「原文」的是 PDF 里写的内容；标「解读」的是我加的解释，不是 PDF 原文，答辩时不要当成老师给的标准答案。

---

## 0. 这份文档在讲什么

PDF 的标题是「六个人，一周，能做完哪些网站？」，副标题一行限定死了范围：

> **6 人 · 8 天 · 可用 AI 工具 · 纯网页，无 App，无硬件**

它给的是 **8 个选题方向**，不是成品网站，也不含现成代码。筛选标准只有一条：

> **按"六个人能并行开工"筛选：每条线都有独立的负责人与交付物。**

也就是说，这份文档真正在解决的不是"做什么好看"，而是"**六个人怎么不互相堵住**"。

### 三条硬约束（原文，第 5 页）

1. **纯网页**：一个链接就能交付
2. **不接任何硬件**
3. **不做成要下载安装的 App**

这三条决定了技术选型上限：一切必须跑在浏览器里，不能依赖传感器外设、串口、蓝牙，也不能指望用户安装任何东西。

## 2. 怎么选（原文，第 2 页）

| 你们的情况 | PDF 的建议 | 理由 |
|---|---|---|
| **人多、想稳** | 06 像素游戏厅 | 一人一款游戏，天然并行，最后一定能合得上 |
| **想拿高分** | 01 3D 非遗数字馆 或 07 线上策展 | 技术深度 + 内容厚度，答辩最有话说 |
| **有人会数据** | 02 一座城的 24 小时 | 六个角色几乎没有重叠，做完像一件真作品 |
| **想两周内稳交** | 03 声音花园 或 08 可交互的教科书 | 规模可控，亮点集中在一处 |

> **解读**：这四行其实对应四种团队状态——**怕合不上**（选 06）、**要分数**（01/07）、**有稀缺技能**（02）、**要保底**（03/08）。反过来说，如果你们六个人里有 3 个都想写 3D，那 01 反而是最危险的选择。

## 3. 最容易翻车的地方（原文）

> 不是做不出来，而是最后一天才发现三块东西合不到一起。**D5 之前必须完成第一次合并。**

> **解读**：这是整份 PDF 里最有价值的一句。六人项目的失败模式几乎从来不是"某个模块做不出"，而是"三个模块各自能跑、拼起来就崩"。所以排期把 D5 定为合并联调日，而不是最后一天。哪怕功能没做完，D5 也必须先合一次。

### 01 · 3D 非遗数字馆 ★★★

**原文一句话**
> 一个链接进去，镜头带你从门口走到匠人的工作台。

**它到底是什么（解读）**
一个纯浏览器内的 3D 虚拟展厅，参观动线是设计好的：进门 → 展厅 → 匠人工作台 → 尾厅。用户不用装任何插件，靠鼠标和滚轮就能走。核心是"**沉浸感 + 内容厚度**"，而不是"3D 技术炫技"。

**要做的功能（原文）**
- 3D 展厅与自由漫游
- 藏品点击弹出说明卡
- 工艺流程分步动画
- 匠人访谈视频嵌入
- 尾厅留言墙

**六人分工（原文）**
| 人 | 负责 |
|---|---|
| ① | 3D 场景与模型 |
| ② | Three.js 交互与性能 |
| ③ | 视觉系统与版式 |
| ④ | 非遗内容考据 |
| ⑤ | 音视频采集与剪辑 |
| ⑥ | 整合、测试与部署 |

**为什么适合 6 人（原文）**
> 3D、内容、影像三条线可以同时开工，互不阻塞。

**交付 / 技术栈（原文）**
- 交付：1 个可漫游 3D 展厅 + 3 段访谈视频
- 技术：Three.js · GLTF · 视频纹理 · 滚动触发

**难点与风险（解读）**
- **性能**：Three.js 场景面数一多，低端笔记本直接掉帧。模型必须提前减面、压缩贴图（KTX2/Draco），这是最容易低估的一块。
- **漫游手感**：自由漫游要么做第一人称相机（容易转晕），要么做固定机位路径（简单但不够"自由"）。建议**固定动线 + 少量自由观察**，别硬做全自由。
- **素材获取**：非遗模型和访谈视频是全组最难搞的外部依赖，D1 就要确认能不能拿到，拿不到立刻换题或换馆。
- **耦合点**：视频纹理、点击弹卡都需要和 3D 场景对接，是典型的"看起来独立、合起来出错"的地方。

**答辩可以怎么讲（解读）**
讲"为什么这个问题必须用网页 3D 解决"——比如"一个非遗项目只有几十个线下观众，但网页能让几千人走进去"。技术点挑一个讲透（例如视频纹理在 3D 空间里的映射），比罗列十个技术名词强。

### 02 · 一座城的 24 小时 ★★★

**原文一句话**
> 把一座城市一天的呼吸，做成能拨动的仪表盘和一篇长报道。

**它到底是什么（解读）**
一个"数据新闻"式作品：左边是可按 0–24 时拖动的地图仪表盘，右边是配套的滚动长报道。它同时具备**可视化**和**叙事**两种能力，是评委最容易判断"你到底做了没做功课"的一类。

**要做的功能（原文）**
- 地图 + 0–24 时时间轴
- 人流、天气、交通多图层
- 点击街区弹出故事卡
- 图表与滚动叙事结合
- 数据来源与口径说明

**六人分工（原文）**
| 人 | 负责 |
|---|---|
| ① | 数据采集与清洗 |
| ② | 地图与图层 |
| ③ | 图表与交互 |
| ④ | 视觉与动效 |
| ⑤ | 数据叙事文案 |
| ⑥ | 前端整合与性能 |

**为什么适合 6 人（原文）**
> 数据、地图、图表、文案四条线天然可分给六人。

**交付 / 技术栈（原文）**
- 交付：1 个数据仪表盘 + 1 篇滚动长报道
- 技术：ECharts · Leaflet · GeoJSON · 预处理 JSON

**难点与风险（解读）**
- **数据来源是第一风险**。真实城市数据（人流、交通）很难拿到，PDF 里专门要求写"数据来源与口径说明"，说明老师会查。**拿不到真数据就必须明确标注是模拟数据**，不能含糊。
- **数据清洗吃时间**：①号位的活最脏，容易成为瓶颈。建议 D1–D2 就把清洗脚本跑通、产出预处理 JSON，后面所有人只吃这份 JSON。
- **叙事和图表容易两张皮**：常见失败是"左边图表能动、右边文章很干"。要求每张图都能用一句话说清它证明了什么。
- **地理编码**：街区名 → 经纬度的对齐会卡住，别在 D1 才试。

**答辩可以怎么讲（解读）**
先讲一个**具体发现**（例如"早 7 点这条街的人流是晚 7 点的 3 倍"），再讲你怎么用图表和地图把它呈现出来。数据新闻的说服力来自结论，不来自图表数量。

### 03 · 声音花园 ★★

**原文一句话**
> 每个人点开，都会长出一片只属于自己声音的森林。

**它到底是什么（解读）**
生成艺术 + 音频输入：用户对着麦克风说话、或上传一段音频，网站把声音特征（频率、节奏、音量）映射成参数，实时"长"出一片独一无二的图形森林，并且可以导出成海报分享。它的卖点是**每个人得到的结果都不一样**。

**要做的功能（原文）**
- 参数驱动的生成视觉
- 麦克风或上传音频输入
- 三种生成模式切换
- 导出海报分享
- 作品长廊

**六人分工（原文）**
| 人 | 负责 |
|---|---|
| ① | 生成算法与噪声 |
| ② | 音频分析与映射 |
| ③ | 视觉与色彩 |
| ④ | 参数面板与交互 |
| ⑤ | 作品长廊与分享 |
| ⑥ | 整合与性能测试 |

**为什么适合 6 人（原文）**
> 算法和视觉可以用假数据先并行推进，最后再对接音频。

**交付 / 技术栈（原文）**
- 交付：1 个生成艺术站 + 1 条作品长廊
- 技术：Web Audio · Canvas / p5.js · 噪声函数

**难点与风险（解读）**
- **"好看"是不可控的**：生成算法很容易做出"能跑但很丑"的东西。必须在 D3 之前就把视觉调参调到能看，否则后期全是推倒重来。
- **麦克风权限**：浏览器需要用户授权，演示环境（教室电脑）可能没麦克风或权限被禁。**必须保留"上传音频"和"示例音频"两条后路**。
- **音频→参数的映射没有标准答案**：这是这个题最大的自由度，也是最大的坑，需要定一个规则并写清楚。
- **分享链路**：导出海报/分享链接涉及 Canvas 导出与状态序列化，容易在最后一天才发现不行。

**答辩可以怎么讲（解读）**
现场让评委说一句话、当场生成一棵树，这是这个题最强的演示优势。讲清"声音特征 → 图形参数"的映射规则，比讲画得多好看更有说服力。

### 04 · 滚动长卷 ★★

**原文一句话**
> 一次向下滚动，读完一条街、一个人或一段历史。

**它到底是什么（解读）**
典型的"滚动叙事"（scrollytelling）长页：用户只做一件事——往下滚，页面按分镜推进图文、动画、地图、影像。技术门槛在八题里最低，但**内容质量要求最高**：做不好就是一篇排版精美的PPT。

**要做的功能（原文）**
- 分镜脚本与首屏宣言
- 滚动触发章节动画
- 地图与时间线穿插
- 影像与插画结合
- 结尾彩蛋与来源说明

**六人分工（原文）**
| 人 | 负责 |
|---|---|
| ① | 脚本与分镜 |
| ② | 摄影与影像 |
| ③ | 插画与图形 |
| ④ | 滚动动效 |
| ⑤ | 文案与信息设计 |
| ⑥ | 前端整合 |

**为什么适合 6 人（原文）**
> 分镜一旦定稿，插画、影像、动效三组可以完全并行。

**交付 / 技术栈（原文）**
- 交付：1 条 6 屏以上的滚动叙事长页
- 技术：CSS sticky · GSAP ScrollTrigger · IntersectionObserver

**难点与风险（解读）**
- **分镜是唯一的依赖点**：分镜不定稿，后面三个人全部空转。D1–D2 必须把分镜钉死，这是这个题的关键路径。
- **内容没有厚度就完了**：技术太简单，全靠选题和文字撑。选一个你们真的能采访到、能拍到、能查到的题材。
- **移动端滚动体验**：桌面端很爽，手机上 sticky 和视差容易错位，是常见翻车点。
- **素材版权**：摄影和插画必须可商用，按团队规则记进 `docs/design/素材来源.md`。

**答辩可以怎么讲（解读）**
这个题答辩要赢在"故事"，不在"技术"。准备一句话讲清"这条街/这个人的转变是什么"，然后展示滚动节奏如何服务于这个转变。

### 05 · 不存在的品牌 ★★★

**原文一句话**
> 给一款虚构的香水做官网：能看、能换、能下单（假流程）。

**它到底是什么（解读）**
一个**虚构品牌的完整官网**：品牌宣言、视觉系统、3D 产品展示、材质配色实时切换、工艺故事页、模拟下单流程。它最像真实商业作品，也最适合放进作品集——但注意下单是**假流程**，不能真的接支付。

**要做的功能（原文）**
- 品牌宣言与视觉系统
- 3D 产品展示
- 材质与配色实时切换
- 工艺故事与内容页
- 模拟购买流程

**六人分工（原文）**
| 人 | 负责 |
|---|---|
| ① | 品牌与视觉系统 |
| ② | 3D 产品与材质 |
| ③ | 页面结构与动效 |
| ④ | 文案与内容 |
| ⑤ | 交互与状态管理 |
| ⑥ | 整合与性能优化 |

**为什么适合 6 人（原文）**
> 品牌、3D、页面三条线独立，能并行到最后。

**交付 / 技术栈（原文）**
- 交付：1 套品牌官网 + 1 个配置器
- 技术：Three.js 材质替换 · 滚动动效 · 品牌网格与字体

**难点与风险（解读）**
- **3D 产品的建模质量决定成败**：一瓶香水的材质（玻璃、金属、磨砂）在网页上渲染好非常难，是最吃功底的一环。
- **"假下单"的边界**：要明确标"demo / 演示数据"，不能让人误以为能真付款，这既是合规也是团队红线。
- **品牌调性容易散**：六个人如果没有统一的视觉规范，最后会做出五个风格。①号位必须在 D2 之前产出色彩、字体、网格三件套。
- **状态管理**：颜色、材质、规格的组合是典型的状态爆炸，⑤号位的活比看起来重。

**答辩可以怎么讲（解读）**
讲"品牌一致性"——从 logo、字体、色彩到 3D 材质如何讲同一个故事。这个题的优势是商业成熟度，弱点是"没有真实用户"，所以要主动讲清设计决策的依据。

### 06 · 像素游戏厅 ★★

**原文一句话**
> 一个复古游戏厅，三台自制卡带机，六个人各管一摊。

**它到底是什么（解读）**
一个复古街机风格的网页大厅：大厅里有卡带墙/机台，点进去是三款各自独立的小游戏，统一 UI、统一最高分记录（localStorage）。**这是八题里分工最不容易打架的结构**——一人一款游戏，开发期几乎零耦合。

**要做的功能（原文）**
- 大厅与卡带墙
- 三款小游戏各自独立
- 统一 UI 与最高分记录
- 音效与彩蛋
- 触屏适配

**六人分工（原文）**
| 人 | 负责 |
|---|---|
| ① | 大厅与视觉系统 |
| ② | 游戏 A 开发 |
| ③ | 游戏 B 开发 |
| ④ | 游戏 C 开发 |
| ⑤ | 音效与素材 |
| ⑥ | 整合与测试 |

**为什么适合 6 人（原文）**
> 一人一款游戏，是六人分工里最不容易打架的结构。

**交付 / 技术栈（原文）**
- 交付：1 个游戏大厅 + 3 款可玩小游戏
- 技术：Canvas 游戏循环 · 键鼠与触屏 · localStorage

**难点与风险（解读）**
- **"约定"比"技术"重要**：三款游戏必须共用一套约定（分辨率、配色、暂停/分数接口、返回大厅方式），否则合起来是三个不同的网站。**D2 之前必须把接口约定写成一页文档。**
- **游戏可玩性**：三款游戏都要"能玩 30 秒不无聊"，这比技术难。别做需要长时间学习的玩法。
- **触屏适配**：手机上没有键盘，方向键要重新设计成屏幕按钮或滑动，是必做项。
- **音效版权**：免费音效站要确认可商用。

**答辩可以怎么讲（解读）**
这个题的杀手锏是**现场可玩**。让评委随便点一个游戏玩 30 秒，比任何 PPT 都有效。讲清"统一约定如何让三款独立游戏变成一个整体"也是加分项。

### 07 · 线上策展 ★★★

**原文一句话**
> 六个人当一次策展团队，办一场只在浏览器里的展览。

**它到底是什么（解读）**
一个虚拟展览：有策展主题和前言、有展厅动线与分区、每个"藏品"可以点开看细节、配语音导览、可以下载展览手册。它和 01 的区别是——**01 强在 3D 空间，07 强在策展内容与展陈逻辑**，不一定要 3D，2D 加缩放交互就可以。

**要做的功能（原文）**
- 策展主题与前言
- 展厅动线与分区
- 藏品卡与细节放大
- 语音导览
- 展览手册下载

**六人分工（原文）**
| 人 | 负责 |
|---|---|
| ① | 策展主题与结构 |
| ② | 内容与考据 |
| ③ | 视觉与版式 |
| ④ | 展陈交互 |
| ⑤ | 图像与音视频处理 |
| ⑥ | 整合上线 |

**为什么适合 6 人（原文）**
> 策展、内容、视觉、交互各有负责人，适合做出厚度。

**交付 / 技术栈（原文）**
- 交付：1 场虚拟展 + 语音导览
- 技术：路由分页 · 缩放交互 · 图片懒加载

**难点与风险（解读）**
- **"策展"不是"把东西摆上去"**：必须有主题、有观点、有取舍。①号位要是只会罗列，做出来就只是个相册。这是这个题最大的分水岭。
- **内容考据成本高**：②号位要查资料、写说明、核对事实，工作量大且不能编。
- **语音导览**：录音、降噪、时间轴对齐都不难但很琐碎，容易拖到最后。
- **图片懒加载**：展品图通常很大，不处理首屏会白屏好几秒，是必做优化。

**答辩可以怎么讲（解读）**
讲"策展逻辑"——为什么选这些展品、为什么这样分区、观众走完会得到什么。技术部分讲缩放交互和导览同步即可。这个题的分数上限高，但**内容空洞就直接崩**。

### 08 · 可交互的教科书 ★★

**原文一句话**
> 把物理、天文、生物里最难懂的一页，做成能拨动的模型。

**它到底是什么（解读）**
科普向交互实验：挑 3–4 个"课本上讲不清"的知识点，做成可拖参数、即时看结果的模拟器，每个实验配一句结论、一个动手任务、一道小测验，再配教师讲解备注。它的定位是**教学工具**，不是炫技动画。

**要做的功能（原文）**
- 3–4 个可调参数实验
- 每个实验一句结论
- 动手任务与知识测验
- 教师讲解备注
- 移动端可用

**六人分工（原文）**
| 人 | 负责 |
|---|---|
| ① | 学科内容与脚本 |
| ② | 模拟算法 |
| ③ | 可视化绘制 |
| ④ | 交互与教学引导 |
| ⑤ | 视觉与插画 |
| ⑥ | 整合与无障碍 |

**为什么适合 6 人（原文）**
> 内容与算法先做原型，联调压力最小。

**交付 / 技术栈（原文）**
- 交付：4 个可交互实验 + 1 套测验
- 技术：Canvas · D3 · 数学模拟 · 滑块控件

**难点与风险（解读）**
- **正确性是硬门槛**：模拟出来的结果必须和物理/数学规律一致，错了就是负分。②号位需要能验证（比如拿解析解对比模拟值）。
- **"可调参数"要真的有教学意义**：调一个参数什么都没变化，是最常见的失败。每个参数都要对应一个"原来如此"的瞬间。
- **无障碍**：PDF 把"整合与无障碍"单列给⑥号位，说明老师会看键盘可达、对比度、语义标签。
- **学科内容不能靠AI编**：公式和结论必须自己核对，团队规则也写了"不编数据"。

**答辩可以怎么讲（解读）**
现场演示"拨一下滑块，结果变了"，并解释这个变化对应课本哪句话。**这是八题里最容易讲清"我解决了什么问题"的一个**，适合不擅长炫技、但有人能讲清楚的组。

## 5. 六个人怎么站（原文，第 5 页）

| 位 | 角色 | 职责 |
|---|---|---|
| ① | 视觉与版式 | 字体、色板、网格；管所有页面的一致性 |
| ② | 前端主程 | 页面结构、组件、路由与部署上线 |
| ③ | 交互与动效 | 滚动、转场，以及那一个"亮点交互" |
| ④ | 内容与文案 | 资料、脚本、图文撰写与校对 |
| ⑤ | 素材 | 3D 模型、影像、数据，按需产出 |
| ⑥ | 整合与测试 | 拉通联调、性能、演示视频，兼 PM |

> **解读**：注意③号位的描述是"**那一个**亮点交互"——不是"所有交互"。这句话在暗示：六人项目不要贪多，把一个交互做到惊艳就够。⑥号位兼 PM，说明必须有人对"能不能合起来"负责。

## 6. 8 天排期（原文）

| 天 | 阶段 | 当天要交付什么 |
|---|---|---|
| D1 | 定题与技术验证 | 跑通最难的那个 Demo：3D 能转、数据能出图、音频能响 |
| D2 | 定系统与骨架 | 视觉规范 + 页面清单，所有页面能点通（哪怕是空壳） |
| D3 | 并行开发一 | 各模块出可用版本：首页、核心交互、数据接入 |
| D4 | 并行开发二 | 二级页面、内容填充、素材补齐 |
| D5 | **合并联调** | 模块之间能跳转，状态与链接不出错 |
| D6 | 动效与细节 | 滚动、转场、加载动画、空状态与错误提示 |
| D7 | 适配与测试 | 手机端、弱网、跨浏览器、键盘可达、性能 |
| D8 | 交付与彩排 | 演示视频、说明页、部署上线、讲三分钟 |

> **解读**：D1 的"跑通最难的那个 Demo"是整个排期的关键——如果 D1 发现 3D 跑不起来，还有时间换题；拖到 D4 就来不及了。D5 的合并是第二道保险。

## 7. AI 用在这四处（原文）

| 用途 | 怎么用 |
|---|---|
| **脚手架** | 让 AI 生成页面骨架、ECharts 配置、Three.js 场景模板，再自己改 |
| **素材** | AI 出插画、贴图、占位图与文案初稿，统一风格后人工修一遍 |
| **内容与测试** | 资料归纳、术语解释、数据清洗脚本、测试用例与 README |
| **红线** | AI 只做初稿与提效；**代码和文案必须自己读懂、自己改，答辩要能讲清** |

> **解读**：这四条实际上是"AI 可以帮你加速，但不能替你理解"。答辩被问到"这段代码为什么这么写"答不上来，是 AI 时代最典型的扣分点。

## 8. 三条硬约束（原文，第 5 页）

1. **纯网页** —— 一个链接就能交付
2. **不接任何硬件**
3. **不做成要下载安装的 App**

> **解读**：这三条排除了一大批想法（AR 眼镜、体感、桌面软件、微信小程序）。评审时如果提案里出现"需要用户下载"或"需要外设"，基本直接出局。

## 9. 我的落地建议（解读，非 PDF 内容）

1. **先按"谁来当⑥号位"选人，再选题。** 六人项目里最稀缺的不是会写 3D 的人，是能拉通联调、盯进度的人。
2. **D1 就做"最丑但能跑"的版本。** 3D 一个方块转起来、数据一张图出来、音频一响，就算验证通过。
3. **把"合并"当成一个功能来排期**，而不是"做完再合"。D5 那天所有人只做一件事：让别人的模块能和自己的模块接上。
4. **每个选题都先回答一句**："这个网页为什么必须是网页？" 答不上来的，说明它其实可以是个 PPT。
5. **风险最高的是外部素材**（非遗模型、城市数据、摄影、音效）。凡是要"去外面找"的东西，D1 就要确认能不能拿到，拿不到立刻降级方案。
