## 0. 结论先行

需求文档本身质量很高：schema 已冻结、QC 清单、伦理条款、验收标准都写了。**需求工程已经做完了，剩下的风险全在执行层。**

> **工程难度中等，比 3D / 数据大屏类选题稳。成败不在代码，在两件事：① 音频生产线；② 地图坐标方案。**

三个判断：

1. **能不能按时交，取决于 D3 有没有 8 条合格的音频**，不取决于前端。
2. **六个人能否真并行，取决于 D1 是否用 3 条假数据先让前端开工**。
3. **最容易返工的地方是底图方案**，它决定 schema 用经纬度还是相对坐标，改晚了全组重做。

## 1. 项目优点

| # | 优点 | 为什么值钱 |
|---|---|---|
| 1 | **素材独家、不可复制** | 闭馆铃、食堂刷卡声是网上抄不到的；评委翻遍作品库也找不到替代品，原创性这一项直接拉满 |
| 2 | **情感共鸣是天然 demo** | 声音比图片更容易触发记忆。答辩现场放 10 秒闭馆铃，比讲 10 页 PPT 有效 |
| 3 | **技术栈风险低** | 静态站 + `sounds.json` 单一数据源 + 现成库（Leaflet / Wavesurfer / html2canvas），无后端、无登录、无数据库，天然满足"纯网站 / 不做 App / 无硬件" |
| 4 | **数据驱动 = 真正能 6 人并行** | schema 冻结后，前端可以拿假数据先开工，不被录音卡住；这是本项目最大的分工红利 |
| 5 | **范围砍得干净** | 明确写了"不做注册 / 上传 / 后台 / AI 识别"，P2 默认砍掉。课程作业里能做到"只做减法"的组，基本都能按时交 |
| 6 | **移动端 + 离线可用** | 音频本地化部署，答辩不依赖现场网络，这是文档里最有价值的一条验收标准 |

## 2. 难点与对策（按翻车概率排序）

### 难点 1｜音频是内容生产，不是写代码 ★★★★★

**表现**

- 8 条 P0 里有一半绑死在时间窗：闭馆铃 21:55、鸟鸣 6:30、雨天滴水（等天气）、社团招新 9:00。10 天里天气和作息不配合，就凑不齐。
- 现场噪声不可控：食堂爆音、风声、路人对话、手机自动增益的抽风。
- 后期是硬技能：降噪、削波修复、**响度统一 -16 LUFS**、转 128k MP3、总大小 ≤ 12 MB。六个人里只要没人会 Audacity 就卡住。

**对策**

- D1 就把 8 条 P0 里的 4 条换成**全天可录**的（食堂、操场、宿舍猫叫、开水房），给天气和作息留余量。
- R4 在 D2 先做出一条"标准成品"当模板（剪辑参数、响度、导出设置），其他人照着剪。
- "每条录 3 遍"是对的，但要按 **×3 的时间成本**排期，不要按 ×1 排。

### 难点 2｜地图坐标系的坑 ★★★★

**表现**

- 高德 / 腾讯瓦片用的是 **GCJ-02**，从别处拿到的经纬度多半是 WGS-84，直接标会偏移 100–500 米 —— 在校园尺度上等于"点错楼"。
- `bounds` 校验只能防"点到校外"，防不了"点在错的楼"；校园内部建筑在地图上往往没有细节，只能肉眼对点。

**对策：D1 必须二选一**

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A 真地图** | Leaflet + 高德瓦片（GCJ-02） | 开发快、能缩放、像"真地图" | key / 配额 / 坐标系 / 断网 四个坑 |
| **B 自绘平面图**（推荐） | SVG 或高清截图描摹 + 相对坐标 | 100% 可控、可离线、视觉统一、更像"作品" | 需要画图（约 2 小时）；schema 的 `lng/lat` 要改成 `x/y` |

> 8–12 个点的校园，真地图的收益远小于它带来的风险。**推荐 B**，代价只是改一次 schema。

### 难点 3｜音频交互的浏览器细节 ★★★

- **自动播放策略**：任何 `play()` 必须在用户手势之后触发；页面加载就 `play()` 会被静音拦截。
- **互斥播放**：切换点位时必须停掉上一条，否则两条同时响，作品当场废。
- **波形与状态同步**：播放进度、波形高亮、弹层状态三者容易不同步。
- **Safari 差异**：iOS 的 audio 行为和 Chrome 不同，必须真机测。
- Wavesurfer 的 v6 / v7 API 不兼容，**版本要锁死**；波形建议**预生成 peaks JSON**，不要运行时 decode 全部音频。

### 难点 4｜数据一致性 ★★★

- 20+ 字段 × 12 条手写，必然出错：`duration` 误差、`id` 与文件名不一致、`status` 忘改、`order` 重复。
- **对策**：写一个约 30 行的 Node 校验脚本，挂在 `prebuild` 上，检查：id 正则、音频文件存在、时长误差 ≤ 1s、坐标在 bounds 内、`story` 50–150 字、`tags` ≤ 5 个、音频总量 ≤ 12 MB。
- 规则：**一个人写 json，一个人审，脚本卡关。**

### 难点 5｜六人并行的协作风险 ★★

- 两人同时改 `sounds.json` → 冲突且难合。约定：**只有 R5 一个人写 json**。
- `story` 由不同人写，50–150 字风格不统一，详情页会被长短不一的文案撑坏 → R1 统一润色一遍。
- 素材命名不规范 → 部署后路径编码 404（"全小写、连字符、不加中文"这条要严格执行）。

### 难点 6｜视觉转译 ★★

声景站最容易做成"技术 demo"：波形 + 地图 + 播放器，冷冰冰。要么有统一的地图色调与字体系统，要么用"声音指纹 / 频谱"做视觉母题。R3 要交的是一套完整视觉方案，不是逐页拼。

### 难点 7｜现场演示 ★★

现场音量、设备、网络。文档里"不依赖现场网络"这条很好，但要真的断网测过，而不是以为测过。

## 3. 分工方案

### 3.1 对需求文档 R1–R6 的两处修正

1. **把"播放器 / 波形"从 R6 挪给 R4** —— 音频工程的人对音频行为最敏感，播放器交给做后期的人，联调成本最低。
2. **"部署"明确归 R2，"上线验收"归 R6** —— 否则两人都以为对方在管，最后没人管。

### 3.2 六人角色表

| 角色 | 主责 | 关键交付物 | 什么算完成 |
|---|---|---|---|
| **R1 项目 / 内容主编**（兼文案） | 排期、schema 冻结、20 条清单认领、story 统一润色、授权审核、答辩 PPT 与演示脚本 | 排期表、8–12 条 story 终稿、3 分钟脚本 | D1 出排期；D8 内容全审完；D10 能脱稿讲 |
| **R2 前端主程** | 脚手架与路由、数据层、地图组件、打点与筛选联动、**校验脚本、构建部署** | 可跑通的地图页 + `npm run build` 可上线 | D3 地图框架跑通；D9 部署稳定 |
| **R3 视觉 / 动效** | 设计系统（色板 / 字体 / 网格）、地图与详情页版式、波形视觉、转场、分享卡 | 一套组件样式 + 详情页 + 分享卡 | D2 出视觉规范；D7 详情页定稿 |
| **R4 音频工程（录音 A）** | A 组录音、降噪 / 响度 / 剪辑 / 编码、**播放器与波形、互斥播放** | 8–12 条合格 MP3 + 播放器 | D3 交 80% 音频；D5 播放器可用 |
| **R5 录音 B / 内容录入** | B 组录音、现场记录表、**坐标采集**、`sounds.json` 录入、封面图 | 全量 `sounds.json` + 封面图 | D4 数据可被前端消费；D8 全绿 |
| **R6 交互 / 测试 / 上线** | 盲听猜地点、移动端适配、兼容性与断网测试、部署验收、回归清单 | 盲听互动 + 测试报告 | D7 互动可用；D9 测试报告 |

### 3.3 人日配比（总 60 人日）

| 角色 | R1 | R2 | R3 | R4 | R5 | R6 |
|---|---|---|---|---|---|---|
| 人日 | 10 | 12 | 10 | 12 | 9 | 7 |

> 参考结构：3 个偏开发 / 交互（R2、R3、R6），2 个音频内容（R4、R5），1 个 PM / 文案（R1）。**不要 6 个人都想写前端。**

### 3.4 三条并行轨道

```text
轨道 A（内容线）  R1 + R4 + R5   录音 → 剪辑 → json → 审核
轨道 B（代码线）  R2 + R6        假数据先做地图 / 播放器 / 盲听 → D5 换真数据
轨道 C（设计线）  R3             D2 出规范，D3 起做详情页 / 分享卡
```

**关键约定（最重要的一条）**

> D1 先塞 3 条**假数据**进 `sounds.json`，B 线全程用假数据开发，D5 一次性换真数据。

这样录音拖延不会让前端空转。否则 3 个人等 1 个人，6 人组的优势就全没了。

### 3.5 录音值班表（D1 就要排，别等 D2）

| 时段 | 负责人 | 目标声音 |
|---|---|---|
| 06:30–08:00 | R4 | 清晨鸟鸣、上课预备铃 |
| 12:00–12:30 | R4 | 食堂刷卡、打菜窗口嘈杂 |
| 17:00–18:00 | R5 | 操场哨声、篮球拍球 |
| 21:00–22:00 | R5 | 闭馆铃、宿舍猫叫、开水房、洗衣房 |

两人都排到班才算完成，**不要"谁有空谁去"**。

### 3.6 关键路径与硬门槛

```text
录音 → 剪辑成品 → json 录入 → 打点绑定 → 详情页联调 → 演示彩排
       ↑
   D3 硬门槛
```

**D3 硬门槛**：8 条合格音频没到位，立刻把范围降到 8 个点、P1 全砍，不许再谈加功能。

### 3.7 协作约定

- `sounds.json` **只有 R5 写**，R1 审核，R2 的校验脚本卡关。
- 素材命名严格执行文档 3.4 节：全小写、连字符、不加中文。
- `raw/` 原始录音不入库、不部署；`final/` 才部署。
- 每天 5 分钟站会，只回答三句：昨天交付了什么 / 今天交付什么 / 卡在哪。

## 5. 与需求文档的 4 处建议修改

1. **1.9 分工表**：按本文 3.2 调整 R4 / R6 / R2 的职责边界。
2. **1.8 里程碑**：D3 增加"8 条合格音频"作为硬门槛，不达标即降范围。
3. **2.2 顶层字段**：若选 B 方案，`campus.center / bounds` 与 `location.lng / lat` 改为相对坐标（`x / y`，0–100 百分比）。
4. **2.6 校验规则**：从"构建前跑一次检查"落实为 `prebuild` 钩子里的 Node 脚本（可直接 npm 运行）。
